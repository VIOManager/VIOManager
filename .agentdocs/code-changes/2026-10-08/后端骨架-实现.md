## Step 0 工程与环境初始化（commit 7730fcb）

**交付**：

- Maven 多模块：父 pom（Spring Boot 3.5.5 + Java 21）+ vio-common 底座 jar + vio-management 服务
- Flyway `V1__init_52_tables.sql`：由 docs/db/initsql.sql 机械转换（剔除头注释 / CREATE DATABASE / USE / 两行 SET FOREIGN_KEY_CHECKS，52 表逐数核对）
- docker-compose.yml 三容器（MySQL 8.4 binlog ROW 14 天 + MinIO + ClamAV）+ .env.example
- `/api/health` 探活接口 + application.yml（数据源/MinIO 全环境变量、gzip 白名单不含 SSE）

**验证结果**：三模块 BUILD SUCCESS；Flyway 迁移成功、库内实测 52 张业务表；health 返回 code=0；binlog 实测 ON / ROW / 1209600 秒。

**偏差与已知项**：

1. minio 镜像当日被镜像加速器故障挡住（六个源均失败），未拉起容器。Step 0 代码零依赖 MinIO，恢复后 `docker compose up -d minio` 补齐即可
2. 宿主端口 3307（本机原生 MySQL 占 3306），compose / .env.example / application.yml 三处一致
3. Boot 3.5.5 自带 Flyway 对 MySQL 8.4 报"未官方测试"WARN，迁移实际成功，暂不处理
4. V1 SQL 约 1223 行，超 300 行规则——契约转换文件，Flyway V1 必须单文件，登记为例外

## Step 1 统一响应与全局异常（本次 commit）

**交付**（全部落 vio-common，阶段2 论坛直接复用）：

| 类 | 职责 |
|----|------|
| `common.result.Result` | 统一响应体，成功 code=0 message="ok"（对齐规范 §2.2 示例） |
| `common.exception.BizException` | 业务异常，携带 ErrorCode |
| `common.exception.GlobalExceptionHandler` | 收敛一切异常为 Result：业务码透传、参数类归 1001（message 说明字段）、路由未命中归 1004、未捕获兜底 1000（堆栈只进日志） |
| `common.enums.ErrorCode` + 三段枚举 | 1000–1007 通用（CommonErrorCode）、2001–2004 认证（AuthErrorCode）、6001–6003 审批（ApprovalErrorCode），枚举统一放 common.enums（规范 §8.1） |

HealthController 已换用 `Result.ok(...)`，Step 0 的裸 Map 与 TODO(Step1) 清偿。

**关键实现决策**（规范未明说、按最保守口径定的，评审请确认）：

1. HTTP 状态码只做两处配对：1002→401、1003→403（规范 §5.1 明文），其余业务码一律 HTTP 200 + 响应体 code 表达
2. 1000 兜底码为方案补充，**规范 §4 通用码表暂无此行**，待下次规范修订登记
3. common 的 web/validation 依赖用 provided——不传递给使用方，由各服务自带 starter

**验证结果**：

- 单测 6/6（ErrorHandlingTest，MockMvc）：6001 透传、1001 缺参带参数名、1001 字段校验带字段名、1000 兜底不带堆栈、1004 路由未命中、health 的 Result 形态
- 实机 curl：`/api/health` → `{"code":0,"message":"ok",...}`；`/api/no-such-route` → `{"code":1004,"message":"资源不存在","data":null}`（Spring 默认错误体已被收敛）
