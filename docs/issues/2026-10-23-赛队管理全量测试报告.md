## 二、发现的问题（按优先级）

### bug#1（B 线后端）关键词搜索不搜项目名
TE01 `TeamQueryServiceImpl.listTeams` 只 `t.name LIKE`（78 行），前端占位符写的是"队名 / 项目名"。搜"1234"（队伍 123 的项目名）返回空。一行修复：`(t.name LIKE ? OR t.project_name LIKE ?)`。

### bug#2（B 线前端 + 种子）手机号列空值显示"无权查看"
`TeamDetailDrawer` 203 行：`m.phone` 为空时渲染"无权查看"——**数据缺失被显示成权限话术**。后端字段裁剪逻辑本身正确（`toMemberVOs` 213-226 行按队长/教师/管理员/本人放行）。叠加种子缺陷：R__ 种子成员没有 phone 数据，演示时该列永远是"无权查看"，验收时极易误判成权限 bug（本次测试就被误导了一轮）。建议：空值显示"—"，种子补 phone。

### bug#3（B 线前端）学生队长添加指导教师必然失败
`openAdvisorPicker` 用 A 线全员接口 `apiMembers(memberType=TEACHER)` 拉候选——该接口仅 SUPER_ADMIN/DEPT_ADMIN（403）。学生队长点"添加"→ 候选永远空 + 降级提示还误导为"教师候选列表依赖 A 线人员接口，后端就绪后可用"（后端早就绪了，是权限拦截）。管理员侧链路正常（本次已验证通过项 13）。需要：受限的教师搜索口（只回 id/姓名/学院）或调整入口归属。

### bug#4（审批中心前端）快照 JSON 雪花 ID 精度丢失
审批详情"申请快照"里 contestId 2111980292808564738 显示为 2111980292808564700——前端 JSON.parse 后重新序列化，超出 JS 2^53 精度。仅显示层（DB 存原文、后端回调读原文均无损），但会误导排查。快照里的 ID 应按字符串处理。

### finding#5（B 线后端）TEAM_CREATE 回调不复查参赛上限
种子单"星辰算法队"（王小明已有 2 支蓝桥杯队）批准后直接建队成为第 3 支——**申请路径会拦"重复参赛"，审批回调不拦**（TeamCreateHandler.onApproved 只复查比赛状态+队名唯一）。与 B 线给 TEAM_ADD_MEMBER 回调补的"锁内三复查"不对齐。风险场景：申请时未超限→排队期间他队先批→回调时已超限。建议补复查。

### finding#6（种子陈旧）805 TEAM_DISSOLVE 演示单是死类型
当前契约 TE12 是直接解散（4009 守卫），代码里没有 TeamDissolveHandler——TEAM_DISSOLVE 类型的审批单**不可能再产生、也没有回调实现**，若演示中被批准会失败。建议从种子删除或换剧情。

### 观察项（低优先级，不必改）
- 学生可直达管理端 /team（路由守卫只查登录态，符合规范 §5.3"后端是权限边界"；后端数据范围已正确兜底，仅 UI 体验问题）
- 全局菜单"论坛"链接硬编码 localhost:5175，Vite 端口漂移后失效（本轮在 5174）
- 无 Redis 时被邀请成员卡"待确认"：确认 4013、退出需 CONFIRMED，只能"拒绝"脱身——联调机需要起 Redis 才能跑完整成员生命周期

## 三、Redis 缺失的影响范围（环境说明）

本机当前无 Redis（compose 的 vio-redis 未起、无本地实例）。`TeamLockSupport`（B 线组队并发修复）在 Redis 不可用时按设计**宁拒不放行**：

- ✗ 邀请入队审批的"批准"→ 4013（审批单保留待处理，起 Redis 后可重批）
- ✗ 成员确认/拒绝的"确认"→ 4013（保持待确认）
- ✓ 建队审批、解散、编辑、加人申请提交、指导教师链路等其余全部流程不受影响

**结论：赛队管理核心链路在无 Redis 环境下可用；成员确认与邀请批准两个流程需 Redis。** 建议联调机常驻 Redis（compose 或本地实例）。
